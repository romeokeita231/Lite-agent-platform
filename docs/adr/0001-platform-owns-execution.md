# 平台拥有执行循环，客户端只提供步骤处理器

Status: accepted（执行模型由 ADR 0005 修订；语言分工由 ADR 0008 取代）

原设计把 `POST /v1/runs/{id}/checkpoint` 开给客户端，由业务侧的 Agent 代码在自己的循环里上报每一步。这等于让客户端定义"什么算一步"：平台既不知道下一步是什么，也无法在进程被杀之后接着跑——"从断点恢复"只能由示例 Agent 自己实现，平台退化成一张带状态列的日志表。本平台改为：一次 Run 的步骤序列由平台定义，业务侧以 Policy 的形式参与每一步，平台逐步调度、逐步落盘、逐步决定下一步。

## Considered Options

- **客户端持有循环 + 确定性重放**（Temporal 的做法）：保住了"业务代码自己写流程"的自由度，代价是 SDK 必须强制确定性——禁随机、禁时钟、外部副作用全部走平台。这是四条路里最贵的一条，而且很难用一句话讲清。
- **平台执行声明式工作流**（YAML/DAG）：步骤语义零歧义、代码最少，但项目会滑向"工作流引擎"，业务侧的示例 Agent 与 SDK 失去存在理由，平台/业务的分工叙事同时失效。

## Consequences

- "杀掉进程后仍能从断点恢复"演示的是**平台**，不是示例 Agent。这是整个项目最值钱的可验证点。
- Trace 的 Span 边界由平台定义，可观测性不再依赖客户端的自觉上报。
- 代价：需要一套 worker 契约（平台怎么派活、怎么收回结果、worker 失联怎么算）。这部分工作量在原设计里完全不存在。
- 降级路径是"平台执行声明式工作流"，**不是**回到客户端记流水。后者砍掉了项目最核心的部分，却保留全部工作量。
