# 这是一套运行时，不是一个小号的 Dify

Status: accepted

有人根据 JD 的职责列表提出：这个项目应当是"缩小版的 Dify"。按职责逐条映射功能，确实会得到一张和 Dify 相似的功能表——模型接入、工具注册、工作流、知识库、多租户。但那张表描述的是**产品**，不是**项目**。Dify 是应用构建平台：重心在画布、发布、集成广度与工作区，它的"一步"由画布上的节点定义。本项目的重心在执行语义：谁拥有循环、崩溃从哪接、超时算谁的、fallback 之后调用方怎么解释结果。它的"一步"由业务侧代码逐次决定。

## 差别不在有没有暂停

Dify 已经有人工介入暂停与恢复，也能从 `workflow_run_id` 重放已执行节点的状态（[Dify Workflow API](https://enterprise-docs.dify.ai/zh/3.11.x/develop/api/guides/workflow)）。所以"我们有 HITL、它没有"这种话不能说。差别在**图是谁画的**：Dify 执行的是作者在画布上连出来的已发布工作流；本项目执行的是业务侧进程每一步现算出来的动作。前者是编排器的产品化，后者是运行时的语义。

## Consequences

- 不做画布、不做应用发布、不做知识库管理界面。做了也只是更差的 Dify。
- 可发现性更差：面试官认得 Dify，不认得 "durable agent runtime"。这个代价由 README 的第一段承担——它必须在 30 秒内说清这是什么。
- 能被 Dify 直接反驳的主张不要说。只讲三类：执行语义的取舍、崩溃与恢复的性质、以及为什么这些不该由业务层各自解决。
- 可以借的一点：Dify 的"应用有已发布版本、运行钉住版本"与 ADR 0002、以及注册制 Agent 定义，是同一条原则在三个地方的同一个答案。
